03 面试可演示改造题

准备几个“能讲、能改、能验证”的小改造，用来证明你真正理解这个项目。

面试演示原则

不要现场做大功能。选择能在 10 到 20 分钟内说清楚影响面的改造题，重点展示定位能力、边界判断和验证意识。

改造题 1：新增一个只读命令

目标

新增 /whoami，返回当前飞书用户、chatId、sessionKey 和群聊隔离模式。

为什么适合面试

它能展示命令链路：消息归一化、命令分发、卡片或文本回复，同时不会引入复杂业务。

改动范围

文件改什么
src/types.ts扩展命令名联合类型
src/bridge/message-normalizer.ts识别新命令
src/bridge/message-handler.ts增加命令处理分支
test/*覆盖命令解析和回复行为

面试话术

“我先选只读命令验证扩展点，因为它不碰 runtime，不碰外部文件，也不改变会话状态。这样可以快速证明命令系统的可扩展性。”

改造题 2：给群聊增加静默模式

目标

新增配置：群聊里只有被 @ 时回复；私聊始终回复。未 @ 的群消息只记录 debug，不发提示。

为什么适合面试

它能展示产品体验和消息噪声控制。群机器人如果对每句话都回复，会严重打扰群聊。

改动范围

文件改什么
src/config/schema.ts配置默认值和校验
src/bridge/conversation-router.ts根据群聊策略决定 accepted
test/conversation-router.test.ts覆盖 @ 和未 @ 两种路径

面试话术

“这不是简单 if 判断，而是路由层的责任。是否接受消息应该在进入 runtime 前决定，否则后面附件下载、session 创建都会产生无意义成本。”

改造题 3：增加文档读取 skill 开关

目标

把 lark-doc-cli skill 做成配置开关：默认自动检测，用户也可以显式关闭。

为什么适合面试

它能展示你对 tool 和 skill 的边界理解：不是所有能力都要常驻进上下文。

改动范围

文件改什么
src/types.ts新增 skill 配置类型
src/config/schema.ts增加默认策略
src/extensions/index.ts根据配置和 lark-cli 检测结果加载 skill
src/extensions/lark-cli-guard.ts保持 IM 写操作拦截

面试话术

“我把 lark-cli 当成可选增强，不把它变成安装门槛。核心桥接能力不依赖 CLI，CLI 只在用户环境具备时补充文档和只读查询能力。”

改造题 4：增强文件发送安全

目标

给 send_file_to_chat 增加 MIME 白名单，避免只靠路径和大小判断。

为什么适合面试

它能展示你把模型输出视为不可信输入。安全不是单点校验，而是多层限制。

改动范围

文件改什么
src/types.ts新增 allowedMimeTypes
src/config/schema.ts默认白名单
src/tools/send-file-to-chat.ts在发送前检测 MIME
test/send-file-to-chat.test.ts覆盖允许和拒绝路径

面试话术

“这个改造不会改变工具的职责，只是在原有路径白名单和大小限制上增加一层内容类型校验。它是增强而不是重构。”

改造题 5：多进程部署方案设计

目标

不一定现场实现，但要能讲清楚如果部署成多个 worker，需要迁移哪些状态。

关键点

当前实现多进程问题演进方案
内存里的 SessionHostManager同一 sessionKey 可能落到不同 worker一致性哈希或单 key 路由
内存里的 pendingDialogs发卡和点卡可能不在同一进程Redis 或共享状态表
JSON store文件锁和跨进程竞争复杂SQLite/Postgres
进程内 activeRun/stop 找不到对应任务sessionKey 固定路由到同一 worker

面试话术

“多进程不是简单把 Map 换 Redis。关键是 active run 和 runtime 本身仍在某个 worker 内，所以需要先保证同一个 sessionKey 被路由到同一个 worker。”

本节小结

准备三个可演示改造即可：一个命令扩展、一个配置策略、一个安全增强。再准备一个多进程设计题，用来应对系统设计追问。
