04 面试速查卡

面试前快速过一遍：项目定位、核心链路、关键取舍、风险和下一步。

30 秒项目介绍

pi-remote-feishu 是一个飞书到 Pi Agent 的远程控制扩展。我把飞书私聊和群聊映射成不同的 Pi 会话，每个会话有独立 runtime、队列和 active run，保证多用户场景下不串上下文、不停错任务、不发错回复。项目还把 Pi 的权限确认适配成飞书卡片，并提供受控的文件回传工具，让 Agent 生成的文件可以安全地发回当前飞书会话。

核心链路

Feishu WebSocket 收到消息
  -> 路由：私聊 / 群聊 / 是否需要 @bot / 白名单
  -> sessionKey：dm / group / group-user
  -> SessionHost：runtime + queue + activeRun
  -> 附件处理：图片 / 小文本 / 大文件
  -> Pi prompt：流式生成
  -> 飞书卡片：处理中 / 停止 / 完成 / 权限确认

最该讲的 5 个设计决策

决策一句话解释
每 sessionKey 一个 runtime把飞书的多用户场景映射成 Pi 的多会话管理模型
per-session queue同会话串行保证上下文顺序，不同会话并行保证吞吐
JSON store 只做映射Pi 自己保存会话历史，store 只记录飞书身份到 Pi session 文件的索引
send_file_to_chat 做成工具由模型主动调用，但发送范围由白名单和上下文限制
lark-cli skill 按需加载扩展飞书文档和只读查询能力，同时禁止 IM 写操作绕过桥接层

高频追问速答

问题回答方向
为什么不用一个全局 session会串上下文、停错任务、发错卡片，飞书必须按会话隔离
为什么不用全局锁全局锁会让一个长任务阻塞所有用户，应该按 sessionKey 串行
群聊和私聊是否冲突不冲突，key 不同，runtime 和队列也不同
Webhook 不做影响什么不影响当前 WebSocket 私聊和群聊，Webhook 只是另一种 transport
lark-cli 是不是必装不是。核心收发用 Feishu SDK，lark-cli 只是可选 skill 增强
工具会不会太多v1 常驻工具很少，飞书文档类能力通过 skill 按需加载
多进程怎么做sessionKey 固定路由到 worker，pending dialog 和 store 外置
最大风险是什么连接可靠性、消息幂等、外部文件安全和多进程状态迁移

模块地图

模块职责

可诚实说明的不足

不足下一步
Webhook transport 只是占位实现同一个 FeishuChannel 接口即可接入
JSON store 适合 v1，不适合多进程升级 SQLite 或 Postgres，并把 pending dialog 外置
WebSocket 可靠性还可增强补充重连策略、消息幂等、发送失败补偿
飞书文档和表格能力还偏 skill 化高频能力沉淀成按需工具，低频能力保留 CLI skill

面试前检查

  1. 能在 30 秒讲清项目价值。
  2. 能画出 Feishu -> Pi -> Feishu 的核心链路。
  3. 能解释为什么必须有 SessionHostManager。
  4. 能说清楚 per-session queue 和全局锁的区别。
  5. 能解释 send_file_to_chat 的安全边界。
  6. 能诚实讲出 Webhook、JSON store、多进程的演进方案。
