1. 配置的层级与优先级

优先级高 ──────────────► 优先级低
CLI 参数  >  项目配置(.pi/feishu.json)  >  用户配置(~/.pi/agent/feishu.json)  >  环境变量

loadConfig 的实现：

export function loadConfig(options: LoadConfigOptions = {}): FeishuConfig {
  const cwd = resolve(options.cwd ?? process.cwd());
  const configPath = findConfigFile(cwd, options.configPath);   // 找配置文件
  const fileConfig = configPath ? readConfigFile(configPath) : {};
  const cliConfig = parsePartialConfig(options);                // CLI 参数也走同一套解析

  return normalizeConfig(mergeConfig(envConfig(), fileConfig, cliConfig), cwd);
}

合并顺序：env → file → cli，后面的覆盖前面的。这是典型的配置分层覆盖模式。

2. 为什么「解析」和「校验默认值」要分开

这是 schema.ts 最重要的设计，也是本项目的教学重点。

2.1 parsePartialConfig —— 宽容解析「部分配置」

export function parsePartialConfig(value: unknown): PartialFeishuConfig {
  if (!isObject(value)) return {};
  ...
  const requireMention = readBoolean(policyValue.requireMention);
  if (requireMention !== undefined) policy.requireMention = requireMention;
  ...
}
  • 输入是 unknown（来自 JSON 文件或环境变量，可能是任何形状）
  • 内部用 readString / readBoolean / readNumber / readStringArray 逐字段校验类型
  • 只保留类型正确的字段；错的字段直接忽略（不抛错）
  • 产出的是 PartialFeishuConfig——可能缺字段，但存在的字段类型一定对
💡 为什么这样设计？

配置文件可能来自用户手写，字段缺失/类型错误很常见。解析阶段宽容，校验阶段严格， 把「坏数据」在边界处理掉——这就是「边界消化坏输入」原则。

2.2 normalizeConfig —— 严格补全默认值

export function normalizeConfig(partial: PartialFeishuConfig, cwd: string): FeishuConfig {
  if (!partial.appId) throw new Error("Missing Feishu appId");
  if (!partial.appSecret) throw new Error("Missing Feishu appSecret");

  const policy: FeishuPolicyConfig = {
    requireMention: partial.policy?.requireMention ?? true,   // 可选项补默认值
    dmEnabled: partial.policy?.dmEnabled ?? true,
    groupEnabled: partial.policy?.groupEnabled ?? true,
    ...
  };
  ...
  return { ... };   // 返回完整配置，所有字段都有确定值
}
  • 必填项缺失 → 抛错（appId、appSecret）
  • 可选项缺失 → 填默认值（?? 默认）
  • 返回的 FeishuConfig 一定是完整的，下游代码可以直接用 config.policy.requireMention 而不用担心 undefined

4. mergeConfig：深一层合并

export function mergeConfig(...configs: PartialFeishuConfig[]): PartialFeishuConfig {
  const merged: PartialFeishuConfig = {};
  for (const config of configs) {
    Object.assign(merged, {
      ...config,
      policy: { ...merged.policy, ...config.policy },      // 嵌套对象要逐层展开合并
      sessions: { ...merged.sessions, ...config.sessions },
      rendering: { ...merged.rendering, ...config.rendering },
      files: { ...merged.files, ...config.files },
      webhook: { ...merged.webhook, ...config.webhook },
    });
  }
  return merged;
}
⚠️ 浅合并的坑

普通浅合并会把子对象整个覆盖。比如 env 里设了 policy.requireMention， 文件里设了 policy.dmEnabled，浅合并会导致文件里的 policy 把 env 的 policy 整个盖掉，丢字段。 这里对 5 个子对象逐层展开合并，保证子对象字段也按优先级叠加。

5. 环境变量与配置文件查找

// 环境变量只覆盖「凭证类」字段
function envConfig(): PartialFeishuConfig {
  return parsePartialConfig({
    appId: process.env.FEISHU_APP_ID,
    appSecret: process.env.FEISHU_APP_SECRET,
    ...
  });
}

// 只找一个配置文件：显式 > 项目级 > 用户级
function findConfigFile(cwd: string, explicitPath?: string): string | undefined {
  if (explicitPath) return resolve(explicitPath);
  const projectPath = join(cwd, ".pi", "feishu.json");
  if (existsSync(projectPath)) return projectPath;
  const userPath = defaultUserConfigPath();   // ~/.pi/agent/feishu.json
  if (existsSync(userPath)) return userPath;
  return undefined;
}

凭证不适合写进配置文件进版本库，所以放环境变量。文件之间不合并，文件整体作为一个层级参与合并。

6. 数据流总结

环境变量 ─┐
配置文件 ─┼─► parsePartialConfig（逐字段校验类型）─┐
CLI 参数 ─┘                                        ├─► mergeConfig（分层覆盖）─► normalizeConfig（补默认值）─► FeishuConfig
✅ 本节小结
概念实现
宽容解析parsePartialConfig：坏字段忽略，好字段保留
严格补全normalizeConfig：必填缺失抛错，可选填默认值
分层覆盖env < 文件 < CLI
深合并子对象逐层展开，不丢字段
