重点决策详解

决策 2：识别「单 active session」瓶颈，引入 SessionHostManager

问题：Pi 的 AgentSessionRuntime 是单 session 模型（终端场景合理）。飞书是多用户、多群、多消息入口——共用一个 runtime 必然串线。

选择：sessionKey → SessionHost 的 Map。每个 host 持有独立 runtime + queue + activeRun + context。

不这么做会怎样（设计文档列举的故障）：

  • A 用户消息进 B 上下文
  • A 生成时 B 的消息触发 session 切换
  • B 点停止误中断 A
  • 权限卡片串线
  • 流式输出发错群
💡 教学点

识别底层模型的约束，再设计上层架构去满足真实场景。这是整个项目最重要的一步思考，比任何具体代码都值钱。

决策 3：每会话一个 PromptQueue，而不是全局锁

替代方案对比：

方案问题
全局锁一个群生成时，所有私聊和其他群全被阻塞（差）
事件循环调度器复杂度高，MVP 不需要
每会话队列 ✅锁粒度 = 隔离粒度，互不阻塞

决策 4：用 AsyncLocalStorage 传递运行上下文

替代方案为什么不行
全局变量并发时互相覆盖，完全错误
改工具签名侵入 Pi SDK 的 ToolDefinition，违背决策 1
闭包注入无法穿透 Pi 内部的工具调用链
AsyncLocalStorage ✅跨调用链传递而不污染签名

决策 5：私聊按用户隔离，群聊默认共享

场景key理由
私聊dm:{userOpenId}一个用户一个上下文，连续
群聊默认group:{chatId}协作场景，大家接力讨论同一问题
群聊可选group-user:{chatId}:{userOpenId}需要个人上下文时开启

教学点：会话粒度是产品决策，不是技术决策。默认值选择「共享」（协作）而不是「隔离」（隐私），符合 MVP 场景。

决策 8：权限确认桥接 ExtensionUIContext

问题：Pi 的扩展权限确认（confirm/select）是 TUI 交互，远程用户看不到。

选择：createFeishuUIContext() 把 select/confirm/notify 桥接成飞书卡片，用 pendingDialogs 注册表挂起 Promise，按钮回调 resolve。

价值：Pi 生态里已有的全部权限交互能力，飞书用户也能用，不用为飞书重新实现一套权限系统。

教学点：桥接的本质是「接口适配」——同一个 Promise 语义，换一个 IO 介质。

决策 9：模型输入按不可信数据对待（三层防线）

send_file_to_chat 的 filePath 是模型生成的，模型也可能被骗/出错：

  1. 路径必须在 allowedOutputDirs 白名单内（防目录穿越）
  2. 必须是文件
  3. 大小不超过 maxUploadBytes

附件处理同样：文件名/sessionKey 消毒，防路径注入。

教学点：即使调用方是「自己人」（模型），也要做输入校验。模型输出同样可能是恶意的或错误的。

决策 10：延迟多租户

选择：不做。只在数据结构里保留 tenantKey 字段。

理由：MVP 是一个飞书应用服务一个团队。多租户意味着 tenant router、tenant policy、tenant billing……复杂度成倍增长。

教学点：为「未来可能的需求」只付「字段的代价」，不付「架构的代价」——YAGNI 原则。

决策 11：宽容解析 + 严格补全的配置系统

选择：

  • parsePartialConfig：逐字段类型校验，坏字段忽略（宽容）
  • normalizeConfig：必填缺失抛错，可选补默认值（严格）
  • mergeConfig：env < 文件 < CLI，子对象逐层合并

教学点：解析阶段宽容、使用阶段严格。坏输入在边界被消化，下游永远拿到完整、类型正确的配置。

决策 12：占位用语义化错误，不用空壳

webhook 和 SQLite 都是「接口已定义、实现未完成」。占位方式是抛带说明的错误，而不是空函数或 TODO 注释。

教学点：未实现的功能要「显式失败」——调用方立刻知道「为什么不能用、怎么绕过」。

已知的待改进点（诚实清单）

项目现状风险
getHost 首次并发无锁，可能双创建两条消息同时到新会话时可能建两个 host（WebSocket 事件基本有序，实际低概率）
evictIdle 无调度没有定时器主动调用空闲会话不回收，内存长期占用
卡片动作的耗时操作同步 await会话切换/删除可能阻塞回调处理
多进程无pendingDialogs、内存 host 都是进程内状态
💡 教学点

架构文档要包含「已知缺陷」——面试被追问时，主动说比被戳穿强。诚实也是设计的一部分。

面试/讲解时的 90 秒版本

🗣️ 说给你听

「这个项目把飞书变成 Pi Agent 的远程交互入口。 核心挑战是 Pi 的运行时是单会话模型，而飞书是多用户多群的—— 所以我按 sessionKey 做了会话隔离：每个会话独立 runtime、独立串行队列、 独立活跃任务标记，用 AsyncLocalStorage 传递当前请求上下文，保证流式输出、 停止操作和权限确认都不会串线。 对外，飞书 SDK 被封装成一个干净接口；对内，Pi 的 UI 上下文被桥接成飞书卡片， 权限确认在远程也能用。模型生成的文件通过注册的 send_file_to_chat 工具直接发回聊天。 整个项目不改 Pi 核心，是一个独立可发布的扩展包。」
