2. 全链路时序图

飞书消息
  │
  ▼ ① routeConversation ── 策略检查 + 生成 sessionKey
  │      ├─ 私聊被禁用？拒绝

  ▼ ④ normalizeMessage ── 拼装 Pi 输入

  │      ├─ /stop → 中断
  │      ├─ /sessions /models /status → 管理卡片

  │

  │      runtimeHost.prompt(input)
  │        ├─ 设置 FeishuUIContext（权限确认桥）

  │        │         │    └─ 权限确认 → ui-context 发卡片 → 等按钮

  │        └─ finally：恢复原 UIContext、清理临时附件
  │      ▼
  │      更新停止卡为「已完成」/「失败」
  │      删除 activeRun、更新 lastUsedAt

3. 逐段精读

3.1 路由：routeConversation

const route = routeConversation(options.config, options.message);
if (!route.accepted) {
  if (route.reason !== "Bot was not mentioned") {
    await options.channel.sendText(options.message.chatId, route.reason, { replyTo: options.message.messageId });
  }
  return;
}

细节：没被 @ 的群消息是静默拒绝——不给群成员刷屏。 其他拒绝原因（私聊被禁用、白名单外）会回复原因，方便用户自查。

3.2 获取 Host：getHost

const host = await options.manager.getHost(route.sessionKey, route.identity);

注意：先拿 host，再做附件处理。因为附件处理需要 host.runtimeHost.supportsImages() 判断模型是否支持图片。

3.3 命令分发

if (await handleCommand({...})) {
  await cleanupTempAttachments(...);  // 命令处理完也要清临时文件
  return;
}

命令处理完直接 return，不进入队列。命令系统的细节在交互一章。

3.4 入队执行（核心）

await host.queue.enqueue(async () => {
  // ① 先发「正在处理」停止卡
  const stopCard = await options.channel.sendCard(
    input.chatId,
    buildStopCard({ sessionKey: input.sessionKey, chatType: input.chatType, ... }),
    { replyTo: input.messageId },
  );

  // ② 登记 activeRun（这样 /stop 或停止按钮能找到这个任务）
  host.activeRun = {
    sessionKey: input.sessionKey,
    chatId: input.chatId,
    messageId: input.messageId,
    startedAt: new Date(),
    abort: async () => { await host.runtimeHost.abort(); },
  };

  try {
    // ③ 真正跑 Pi
    await host.runtimeHost.prompt(input);
    // ④ 成功 → 更新停止卡
    await options.channel.updateCard(stopCard.messageId, buildStopDoneCard("Pi 已完成", "回复已生成完成。"));
  } catch (error) {
    // ⑤ 失败 → 更新停止卡为失败信息，并向上抛
    await options.channel.updateCard(stopCard.messageId, buildStopDoneCard("Pi 失败", message));
    throw error;
  } finally {
    // ⑥ 无论成败：清掉 activeRun、刷新最后使用时间
    delete host.activeRun;
    host.lastUsedAt = new Date();
  }
});
💡 「任务状态卡片」设计

任务开始 → 黄卡「Pi 正在处理」+ 停止按钮；任务结束 → 更新同一张卡为完成/失败（灰卡）。 为什么用「更新同一张卡」而不是「再发一条新消息」？因为飞书卡片可以原地更新，避免聊天区刷屏。

3.5 runtimeHost.prompt 内部

async prompt(input: NormalizedPiInput): Promise<void> {
  const uiContext = createFeishuUIContext();          // 权限确认桥
  const previousUIContext = this.runtime.session.extensionRunner.getUIContext();
  this.runtime.session.extensionRunner.setUIContext(uiContext, "rpc");

  try {
    await runWithFeishuContext(
      { sessionKey, chatId, messageId, channel, uiContext, config },
      async () => {
        await renderPromptStream({
          config, channel, chatId, replyTo: input.messageId,
          session: this.runtime.session,
          runPrompt: async () => {
            await this.runtime.session.prompt(input.text, {
              streamingBehavior: "steer",
              ...(input.images.length > 0 ? { images: input.images } : {}),
            });
          },
        });
      },
    );
  } finally {
    this.runtime.session.extensionRunner.setUIContext(previousUIContext, "tui");
    await cleanupTempAttachments(this.config.files.tempDir ?? ".", this.sessionKey).catch(() => {});
  }
}

关键点：

  1. UIContext 切换：执行期间把 Pi 的 UI 上下文替换为飞书版，执行完恢复原值。这是「借用」Pi 的 UI 通道，用完必须还回去。
  2. AsyncLocalStorage：runWithFeishuContext 包裹住整个 prompt，让工具/回调能取到当前 chat。
  3. 图片：模型支持图片才传 images，否则图片在附件层已被降级为文本说明。
  4. finally 清理：prompt 结束必然清理临时附件和 UI 上下文，即使报错。

这就是 message-normalizer 的产出——把飞书侧的元信息织进 prompt，让模型知道「谁在哪个群里、以什么模式」提问。

5. 并发与隔离验证

同一条链路，在不同会话上并行发生：

t=0s  用户A 私聊发「写个网站」→ queue(dm:A) 开始跑
t=0s  群G 发「@机器人 看下报错」→ queue(group:G) 开始跑
t=1s  用户A 又发「加个登录」→ 进入 queue(dm:A) 排队
       └─ dm:A 的队列深度 = 2，group:G 完全不受影响
t=2s  用户B 点停止卡 → 只 abort 当前 sessionKey 的 activeRun

这一切由三件事保证：

  1. queue 隔离：同 sessionKey 串行，不同 sessionKey 独立
  2. host 隔离：每 sessionKey 有独立 runtime 和状态
  3. context 隔离：AsyncLocalStorage 让每个 run 有独立的「我是谁」
