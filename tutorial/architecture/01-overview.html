01 项目概览

这个项目是什么？它解决了一个什么样的核心问题？源码目录长什么样？

🎯 本节目标
  • 能用一句话说清这个项目是干什么的
  • 理解核心难题：Pi 的单会话模型 vs 飞书的多用户并发
  • 认识源码目录结构和依赖技术栈

1. 这个项目是什么

一句话定义：把飞书变成 Pi Agent 的「远程终端」—— 用户在飞书私聊/群聊里发消息，Pi 在服务器上干活，把思考过程、工具调用、生成的文件全部投射回飞书。

┌─────────────────┐        ┌───────────────────────┐        ┌──────────────┐
│  飞书 App       │  ◄────► │  pi-feishu 服务进程    │  ◄────► │  Pi Agent    │
│  (私聊/群聊)     │  WebSocket│ (transport host)      │   SDK   │  (runtime)   │
└─────────────────┘        └───────────────────────┘        └──────────────┘

它不是一个独立聊天机器人，而是 Pi 的一个 transport（传输通道）扩展包。 注意关键词：扩展包——它不改 Pi 核心代码，只通过 SDK 公开 API 接入。

2. 它解决的核心问题（本章最重要）

Pi Agent 的设计目标是终端使用场景，它的核心运行时 AgentSessionRuntime 是单 active session 模型：

AgentSessionRuntime
  -> runtime.session         // 当前只有一个活动 session
  -> runtime.switchSession()
  -> runtime.newSession()

终端里天然只有一个「当前对话」，所以这个模型没问题。 但飞书是多用户、多群、多消息入口。如果所有飞书消息共用一个 runtime.session，会出大乱子：

场景出什么问题
A 用户发消息消息进入 B 用户的上下文，串线
A 生成时 B 发消息触发 session 切换，A 的任务被打断
B 点「停止生成」误中断 A 的任务
权限确认卡片两个用户同时等待确认，resolve 串线
流式输出发错群、发错私聊

因此本项目引入了会话隔离架构（下一章会详细展开）：

ConversationRouter
  -> SessionHostManager
       -> dm:alice        -> SessionHost A -> Runtime A + Queue A
       -> dm:bob          -> SessionHost B -> Runtime B + Queue B
       -> group:chat-123  -> SessionHost C -> Runtime C + Queue C

每个会话（某个私聊用户 / 某个群）拥有独立的 Pi runtime、串行队列、活跃任务标记和飞书上下文， 互不干扰，还能并发运行。

💡 为什么这是「项目的第一性原理」

整个项目的所有代码，几乎都在为「在单会话模型之上实现多会话隔离」服务。 你先记住这个矛盾，后面每一章都能对上号。

3. 两个进程的边界（第二重要的认知）

项目拆成两个独立部分，这是整份代码的骨架：

Transport Host（传输服务进程）Pi Extension（Pi 扩展）
入口src/bin/pi-feishu.ts，命令 pi-feishu servesrc/extensions/index.ts
运行方式长期运行的长连接进程被 Pi 自己加载（package.json 的 pi.extensions 字段）
职责连接飞书 WebSocket、接收消息、处理卡片、维护会话、调用 Pi runtime注册工具（send_file_to_chat）、注册 /feishu 命令、注入 prompt 指引
会不会打开飞书连接会（这是它的本分）不会

为什么拆开？transport host 是「嘴和耳朵」，extension 是「手」。 两者解耦后：不启动 transport 时 Pi 依然正常使用；extension 不需要关心飞书 SDK 细节。

4. 源码目录结构

src/
├── bin/
│   └── pi-feishu.ts          # CLI 入口：解析参数、组装组件、启动服务
├── config/
│   ├── schema.ts             # 配置的类型解析/合并/默认值
│   └── load-config.ts        # 配置加载：env < 文件 < CLI
├── feishu/
│   ├── channel.ts            # 飞书通道封装（SDK 的皮，屏蔽原始类型）
│   ├── context.ts            # 飞书运行上下文（AsyncLocalStorage 魔法）
│   └── webhook.ts            # Webhook transport（占位，未实现）
├── bridge/                   # ★ 核心业务层：飞书世界和 Pi 世界的桥
│   ├── conversation-router.ts    # 消息 → sessionKey 映射规则
│   ├── message-normalizer.ts     # 飞书消息 → Pi 输入
│   ├── session-host-manager.ts   # 会话宿主管理
│   ├── runtime-host.ts           # 单个 Pi runtime 的封装
│   ├── prompt-queue.ts           # 每会话串行队列
│   ├── message-handler.ts        # 消息处理主流程
│   ├── stream-renderer.ts        # Pi 事件流 → 飞书流式输出
│   ├── ui-context.ts             # Pi UI 上下文 → 飞书卡片
│   └── card-actions.ts           # 飞书卡片按钮 → 管理操作
├── cards/                    # 飞书卡片 JSON 构建器
│   ├── common.ts             # 卡片基础组件
│   ├── help / models / sessions / status / stop / permission.ts
├── attachments/
│   ├── processor.ts          # 附件下载与分类
│   ├── mime.ts               # MIME 推断、文本判断
│   └── temp-files.ts         # 临时文件写入与清理
├── store/
│   ├── store.ts              # 存储工厂（json / sqlite 占位）
│   └── json-store.ts         # JSON 文件存储（会话映射持久化）
├── tools/
│   └── send-file-to-chat.ts  # Pi 工具：模型生成文件后发回飞书
├── extensions/
│   └── index.ts              # Pi 扩展入口
├── index.ts                  # 包对外导出
└── types.ts                  # ★ 全部类型定义（建议第一个读的文件）

✅ 本节小结
  • 这是一个 transport 扩展包：不改 Pi 核心，把飞书接进来
  • 核心难题：飞书多用户并发 vs Pi 单 session 模型，用 SessionHostManager 解决
  • 两个进程：pi-feishu serve（传输）+ Pi extension（能力注册）
  • src/types.ts 是全部类型的地基，建议最先读
