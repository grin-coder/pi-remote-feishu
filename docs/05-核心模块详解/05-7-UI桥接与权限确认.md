# 05-7 UI 桥接与权限确认

> 对应源码：`src/bridge/ui-context.ts`、`src/feishu/context.ts`

## 1. 这是什么（整个项目最亮眼的设计之一）

Pi 的扩展系统给插件提供了一个 `ExtensionUIContext`，让插件能：
`ctx.ui.confirm()`（确认）、`ctx.ui.select()`（选择）、`ctx.ui.notify()`（通知）……

在终端里，这些会弹出 TUI 交互。但我们的场景是飞书——**用户根本不看终端**。

`ui-context.ts` 做的事就是：**把 Pi 的 UI 调用翻译成飞书卡片，再把用户点击翻译回 Promise 的结果**。

```
Pi 工具调用 ctx.ui.confirm("是否执行危险命令？")
  └─► 飞书卡片「Permission required - 是否执行危险命令？ [Yes] [No]」
        └─► 用户点 Yes
              └─► Promise resolve("Yes")
                    └─► 工具继续执行
```

**一个在终端里的同步确认流程，被无缝搬到远程飞书上。** 这是 Pi 现有生态能力在远程的复用。

## 2. 核心机制：pendingDialogs

```ts
interface PendingDialog {
  resolve(value: string | undefined): void;
  timer: ReturnType<typeof setTimeout>;
}

const pendingDialogs = new Map<string, PendingDialog>();
```

**一个「等待中的对话框」注册表**：dialogId → resolve 函数 + 超时定时器。
这是「异步请求挂起、等远程用户响应」的标准模式。

## 3. select：发卡片并挂起

```ts
async select(title, options, opts) {
  const context = getFeishuContext();          // ① 从异步上下文拿当前 chat
  if (!context) return options[0];             // 没有飞书上下文 → 返回默认选项

  const dialogId = randomUUID();               // ② 唯一 id
  const timeout = opts?.timeout ?? 60_000;

  return await new Promise<string | undefined>((resolve) => {
    // ③ 注册挂起对话框
    const timer = setTimeout(() => {
      pendingDialogs.delete(dialogId);
      resolve(undefined);                      // 超时 → resolve(undefined)
    }, timeout);
    pendingDialogs.set(dialogId, { resolve, timer });

    // ④ 支持 AbortSignal（调用方取消）
    if (opts?.signal) {
      if (opts.signal.aborted) {
        pendingDialogs.delete(dialogId);
        clearTimeout(timer);
        resolve(undefined);
        return;
      }
      opts.signal.addEventListener("abort", () => {
        pendingDialogs.delete(dialogId);
        clearTimeout(timer);
        resolve(undefined);
      }, { once: true });
    }

    // ⑤ 发飞书卡片
    context.channel.sendCard(context.chatId, buildPermissionCard(title, options, dialogId)).catch(() => {
      pendingDialogs.delete(dialogId);
      clearTimeout(timer);
      resolve(undefined);                      // 发卡失败也不能挂死
    });
  });
}
```

### 3.1 四种退出路径（教学重点）

`Promise` 必须保证**一定会 resolve**，否则工具会永久挂起。这里有四条路径：

| 路径 | 触发 | 结果 |
|---|---|---|
| 正常 | 用户点卡片按钮 | resolve(选项值) |
| 超时 | 60 秒无人点 | resolve(undefined) |
| 取消 | AbortSignal 触发 | resolve(undefined) |
| 发卡失败 | sendCard 抛错 | resolve(undefined) |

**所有异步 UI 挂起都必须有超时和失败兜底**，这是远程 UI 桥接的黄金法则。

## 4. confirm：用 select 组合

```ts
async confirm(title, message, opts) {
  const text = message ? `${title}\n\n${message}` : title;
  const choice = await this.select(text, ["Yes", "No"], opts);
  return choice === "Yes";
}
```

confirm 就是只有两个选项的 select。组合而非重复实现。

## 5. resolvePermissionCardAction：卡片回调入口

用户点按钮后，飞书回调进 `card-actions.ts` → `handleCardAction` → `cmd === "permission"` 分支：

```ts
export function resolvePermissionCardAction(value: Record<string, unknown>): string | undefined {
  const dialogId = typeof value.dialogId === "string" ? value.dialogId : undefined;
  if (!dialogId) return undefined;
  const pending = pendingDialogs.get(dialogId);
  if (!pending) return undefined;
  pendingDialogs.delete(dialogId);            // ① 从注册表移除（一次性）
  clearTimeout(pending.timer);                // ② 取消超时
  const choice = typeof value.choice === "string" ? value.choice : undefined;
  pending.resolve(choice);                    // ③ 唤醒挂起的 Promise
  return choice;
}
```

三件事：**删注册、清定时器、resolve**。顺序很重要——先删后 resolve，保证不会二次触发。

## 6. notify：单向通知

```ts
notify(message, type) {
  const context = getFeishuContext();
  if (!context) return;
  const prefix = type === "error" ? "Error: " : type === "warning" ? "Warning: " : "";
  context.channel.sendText(context.chatId, `${prefix}${message}`).catch(() => {});
}
```

不需要挂起，发一条文本即可。`.catch(() => {})` 保证通知失败不影响主流程。

## 7. 空实现：其余 UI 方法

```ts
input() { return undefined; }
onTerminalInput() { return () => {}; }
setStatus() {}
...
custom() { throw new Error("Custom UI is not available in Feishu mode"); }
getTheme() { return undefined; }
setTheme() { return { success: false, error: "Themes are not available in Feishu mode" }; }
```

`ExtensionUIContext` 接口方法很多，飞书模式下大部分**没有意义**（终端 UI 专属）。
处理策略：

- **无意义但安全的** → 空实现
- **无法支持的**（custom UI、主题）→ 显式抛错/返回错误对象

教学点：**实现一个大型接口时，对不支持的成员用「显式失败」而非「静默忽略」**，
这样调用方会立刻知道该能力在飞书下不可用，而不是陷入莫名其妙的 bug。

## 8. 完整闭环

```
工具执行 → ctx.ui.confirm(...)
  → select() 从 AsyncLocalStorage 拿到 FeishuContext
  → pendingDialogs.set(dialogId, ...)
  → channel.sendCard(chatId, permission卡{cmd:"permission", dialogId, choice:"Yes"})
      │
      ▼ （用户点按钮）
  channel.onCardAction
  → handleCardAction
  → cmd === "permission"
  → resolvePermissionCardAction(value)  ← 从按钮 value 里读 dialogId + choice
  → pending.resolve("Yes")
      │
      ▼
  select 的 Promise 完成 → confirm 返回 true → 工具继续执行
```

## 9. 潜在的注意点

1. **卡片动作与消息的并发**：如果 SDK 串行处理同一 chat 的消息和卡片动作，确认可能被卡住。
   项目已在 `channel.ts` 关闭 SDK chatQueue（见 05-1），保证卡片动作能立刻处理。
2. **dialog 是进程内的**：`pendingDialogs` 是模块级 Map，多进程部署时无法共享（单进程 MVP 没问题）。
3. **多会话安全**：`getFeishuContext()` 返回的是当前 run 的 chatId，
   所以 A 会话的权限卡绝不会被 B 会话的用户点掉——**对话框天然绑定对话上下文**。

## 10. 小结

| 方法 | 机制 | 教学点 |
|---|---|---|
| select | 发卡 + 挂起 Promise | 四种退出路径兜底 |
| confirm | select 的组合 | 组合优于重复 |
| notify | 单向文本 | 失败不阻塞 |
| resolve | 删注册→清定时器→resolve | 一次性语义 |
| 其他方法 | 空实现 / 显式失败 | 大接口的务实实现策略 |
