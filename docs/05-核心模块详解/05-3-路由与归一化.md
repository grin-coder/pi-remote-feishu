# 05-3 路由与归一化

> 对应源码：`src/bridge/conversation-router.ts`、`src/bridge/message-normalizer.ts`

这一篇讲「飞书消息进来后，如何变成 Pi 能懂的东西」的两步转换。

## 1. 路由（conversation-router）

### 1.1 作用

回答两个问题：
1. **这条消息该不该接受？**（策略检查）
2. **该进哪个会话？**（sessionKey）

### 1.2 策略检查链

```ts
export function routeConversation(config: FeishuConfig, message: FeishuMessage): ConversationRouteResult {
  if (message.chatType === "private" && !config.policy.dmEnabled) {
    return { accepted: false, reason: "Private chats are disabled" };
  }
  if (message.chatType === "group" && !config.policy.groupEnabled) {
    return { accepted: false, reason: "Group chats are disabled" };
  }
  if (message.chatType === "group" && config.policy.requireMention && !message.mentionedBot) {
    return { accepted: false, reason: "Bot was not mentioned" };
  }
  if (!contains(config.policy.allowUsers, message.userOpenId)) {
    return { accepted: false, reason: "User is not allowed" };
  }
  if (!contains(config.policy.allowChats, message.chatId)) {
    return { accepted: false, reason: "Chat is not allowed" };
  }
  ...
}
```

检查顺序：**开关 → @ 校验 → 白名单**。
注意 `contains` 的语义：

```ts
function contains(list: readonly string[] | undefined, value: string): boolean {
  return list === undefined || list.includes(value);
}
```

**白名单未配置 = 允许所有人**。这是「默认开放、按需收紧」的安全模型。
（安全模型的选择在 07 里有专门讨论。）

### 1.3 结果类型：用 union 表达「成或败」

```ts
export type ConversationRouteResult =
  | { accepted: true; sessionKey: string; identity: FeishuIdentity }
  | { accepted: false; reason: string };
```

TypeScript 的可判别联合（discriminated union）——`accepted` 字段就是判别标志。
调用方只需：

```ts
if (!route.accepted) { /* 拒绝分支 */ }
// 此处 TypeScript 自动收窄：route 只剩 accepted: true 的形状
```

这种写法避免了「返回 undefined 表示失败」的隐晦，也避免了「返回对象 + 错误码」的啰嗦。
**推荐在结果可能成/败的 API 里使用。**

### 1.4 buildSessionKey

```ts
export function buildSessionKey(config: FeishuConfig, identity: FeishuIdentity): string {
  if (identity.chatType === "private") return `dm:${identity.userOpenId}`;
  if (config.sessions.groupScope === "per-user") return `group-user:${identity.chatId}:${identity.userOpenId}`;
  return `group:${identity.chatId}`;
}
```

三个格式，对应三种会话粒度（详见 `03-核心概念.md` §1）。

## 2. 归一化（message-normalizer）

### 2.1 作用

把 `FeishuMessage`（飞书形状）+ `route`（会话信息）转换成 `NormalizedPiInput`（Pi 形状）。

### 2.2 命令识别

```ts
const COMMANDS = new Set(["help", "sessions", "models", "new", "stop", "reset", "status"]);

function parseCommand(text: string): FeishuCommand | undefined {
  const trimmed = text.trim();
  if (!trimmed.startsWith("/")) return undefined;
  const withoutSlash = trimmed.slice(1);
  const [name = "", ...rest] = withoutSlash.split(/\s+/);
  if (!COMMANDS.has(name)) return undefined;
  return { name: name as FeishuCommand["name"], args: rest.join(" ") };
}
```

- 以 `/` 开头才尝试解析
- 不在集合里的命令返回 `undefined` → 视为普通消息（**未知命令不转发**，这是设计决策，见 07）
- 命令带参数：`/models high` 的 `high` 会进 `args`（虽然当前卡片交互不用它）

### 2.3 去 @ 前缀

```ts
function stripBotMention(text: string): string {
  return text.replace(/^@\S+\s*/, "").trim();
}
```

群聊里用户的消息通常是 `@机器人 帮我看下...`，**@ 前缀必须剥掉**，否则会污染 prompt。

### 2.4 拼装 prompt（核心教学点）

```ts
const text = options.message.chatType === "group"
  ? stripBotMention(options.message.text)
  : options.message.text.trim();

const promptTextParts: string[] = [];

if (text.length > 0) {
  if (options.message.chatType === "group") {
    const sender = options.message.senderName ?? options.message.userOpenId;
    const groupMode = options.route.sessionKey.startsWith("group-user:") ? "per-user session" : "shared chat session";
    promptTextParts.push(
      [
        "[Feishu group message]",
        `Sender: ${sender}`,
        `Session mode: ${groupMode}`,
        "Reply naturally to the sender in the group. Keep the answer concise unless the user asks for detail.",
        "Message:",
        text,
      ].join("\n"),
    );
  } else {
    promptTextParts.push(text);
  }
}
if (attachmentNotes.length > 0) {
  promptTextParts.push(attachmentNotes.join("\n"));
}

const normalized: NormalizedPiInput = {
  ...
  text: promptTextParts.join("\n\n"),   // 用空行分隔各部分
  ...
};
```

几个值得学的点：

1. **群聊消息是「结构化注入」**，不是直接透传。飞书侧元信息（发送者、会话模式）被打包成固定格式，模型拿到的是结构清晰、可理解的上下文。
2. **还给模型行为指令**："Reply naturally... Keep the answer concise"——这是 prompt 工程，让群聊回答更符合场景。
3. **附件说明拼接**：附件处理产出的 `attachmentNotes` 追加在用户文本后面。
4. **各部分用 `\n\n` 连接**，给模型清晰的段落边界。

### 2.5 输出形状

```ts
{
  sessionKey: "group:oc_xxx",
  chatId: "oc_xxx",
  messageId: "om_xxx",
  userId: "ou_xxx",
  chatType: "group",
  text: "[Feishu group message]\nSender: 张三\n...",
  images: [],                // 或 base64 图片数组
  attachmentNotes: [],
  senderName: "张三",        // 有才带
  command: undefined,        // 是命令才有
}
```

可选字段用展开操作符按需添加，保持对象最小。

## 3. 测试对照

`test/conversation-router.test.ts` 验证了路由的 4 种典型场景：

| 场景 | 期望 |
|---|---|
| 私聊 | `dm:alice` |
| 群聊（默认 shared） | `group:chat-1` |
| 群聊（per-user 配置） | `group-user:chat-1:alice` |
| 群聊未 @ | 拒绝 `Bot was not mentioned` |

测试里构造了完整的 `FeishuConfig` 和 `FeishuMessage` fixture——**这也是很好的测试写法**：辅助函数 `config()` / `message()` 让每个用例只写差异部分。

## 4. 小结

| 步骤 | 输入 → 输出 | 关键点 |
|---|---|---|
| 路由 | 消息 → sessionKey 或拒绝原因 | 可判别联合、默认开放白名单、@ 校验 |
| 归一化 | 消息+路由 → Pi 输入 | 去@、命令识别、群聊结构化 prompt |
