# 05-5 运行时封装（RuntimeHost）

> 对应源码：`src/bridge/runtime-host.ts`

## 1. 角色定位

`RuntimeHost` 是**单个 Pi runtime 的管家**。它解决一个关键问题：

> Pi SDK 的 `AgentSessionRuntime` 创建流程很复杂（services、sessionManager、extension 绑定……），
> 而且每次 prompt 都要做 UI 上下文切换、飞书上下文注入、清理工作。
> 这些复杂度不能让业务代码（message-handler）直接面对，于是封装成 `RuntimeHost`。

## 2. 创建 runtime（createRuntimeHost）

```ts
export async function createRuntimeHost(options: {
  sessionKey: string;
  sessionFile?: string;   // 可选：恢复历史会话
  cwd: string;
  config: FeishuConfig;
  channel: FeishuChannel;
}): Promise<RuntimeHost> {
  const cwd = resolve(options.cwd);
  const agentDir = getAgentDir();
  const sessionManager =
    options.sessionFile && existsSync(options.sessionFile)
      ? SessionManager.open(options.sessionFile, undefined, cwd)   // ① 恢复：打开历史文件
      : SessionManager.create(cwd);                                 // ② 新建：空会话

  const createRuntime: CreateAgentSessionRuntimeFactory = async ({
    cwd: runtimeCwd, agentDir: runtimeAgentDir,
    sessionManager: runtimeSessionManager, sessionStartEvent,
  }) => {
    const services = await createAgentSessionServices({
      cwd: runtimeCwd,
      agentDir: runtimeAgentDir,
      resourceLoaderOptions: {
        extensionFactories: [{
          name: "pi-remote-feishu-runtime",
          hidden: true,
          factory(pi) {
            pi.registerTool(createSendFileToChatTool(options.config));   // ③ 注入发文件工具
          },
        }],
      },
    });
    return {
      ...(await createAgentSessionFromServices({ services, sessionManager: runtimeSessionManager, ... })),
      services,
      diagnostics: services.diagnostics,
    };
  };

  const runtime = await createAgentSessionRuntime(createRuntime, { cwd, agentDir, sessionManager });
  await runtime.session.bindExtensions({});   // ④ 绑定扩展
  return new RuntimeHost({ sessionKey: options.sessionKey, runtime, config: options.config, channel: options.channel });
}
```

教学点：

1. **恢复 vs 新建**：`sessionFile` 存在则 `SessionManager.open`，否则 `create`。一个三元判断决定了「老用户接着聊」还是「新用户从头开始」。
2. **工具注入的时机**：`send_file_to_chat` 不是全局注册，而是在**每个 runtime 创建时通过 extensionFactory 注册**——这样每个会话的工具都绑定它自己的 config。注意：`runtime.session.bindExtensions({})` 之后工具才会真正生效（newSession/switch 后都要重新 bind，见 05-4）。
3. **封装 Pi SDK 的复杂初始化**：`createAgentSessionServices` → `createAgentSessionFromServices` → `createAgentSessionRuntime` 三部曲全部收敛在这里，业务层永远不需要知道。

## 3. prompt：执行一次对话

```ts
async prompt(input: NormalizedPiInput): Promise<void> {
  // ① 创建飞书 UI 上下文（权限确认桥）
  const uiContext = createFeishuUIContext();
  const previousUIContext = this.runtime.session.extensionRunner.getUIContext();
  this.runtime.session.extensionRunner.setUIContext(uiContext, "rpc");   // ② 替换为飞书版

  try {
    await runWithFeishuContext(                                          // ③ 注入飞书上下文
      { sessionKey: this.sessionKey, chatId: input.chatId, messageId: input.messageId,
        channel: this.channel, uiContext, config: this.config },
      async () => {
        await renderPromptStream({                                       // ④ 流式渲染入口
          config: this.config,
          channel: this.channel,
          chatId: input.chatId,
          replyTo: input.messageId,
          session: this.runtime.session,
          runPrompt: async () => {
            await this.runtime.session.prompt(input.text, {
              streamingBehavior: "steer",                                // ⑤ 流式行为
              ...(input.images.length > 0 ? { images: input.images } : {}),
            });
          },
        });
      },
    );
  } finally {
    this.runtime.session.extensionRunner.setUIContext(previousUIContext, "tui");  // ⑥ 恢复原 UI 上下文
    await cleanupTempAttachments(this.config.files.tempDir ?? ".", this.sessionKey).catch(() => {});
  }
}
```

### 3.1 逐点讲解

**① UI 上下文是什么？**
Pi 的 extension 可以用 `ctx.ui.confirm()/select()/notify()` 和用户交互。
飞书模式下，这些 UI 能力被 `createFeishuUIContext()` 桥接成飞书卡片（详见 05-7）。

**② 为什么 setUIContext 又恢复？**
Pi 的 session 只有一个 UI 上下文槽位。执行期间我们要「借用」它给飞书桥，
**执行完必须恢复成原来的**（TUI 模式），否则 Pi 终端界面的 UI 就坏了。
参数 `"rpc"` / `"tui"` 是 Pi SDK 要求的来源标识。

**③ 为什么 runWithFeishuContext 要包住整个 prompt？**
prompt 执行期间，模型可能任意时刻调用工具（`send_file_to_chat`）或触发权限确认，
这些回调需要知道「当前在哪个 chat」。AsyncLocalStorage 让整个异步树共享这份 context。

**④ renderPromptStream 做什么？**
订阅 Pi session 事件流，把 delta 实时转发给飞书（详见 05-6）。

**⑤ streamingBehavior: "steer"**
Pi SDK 的流式行为选项，steer 模式下模型输出会受用户后续输入影响（可以中途打断调整方向）。

**⑥ finally 的清理是双保险**
- 恢复 UI 上下文
- 清理本次会话的临时附件（图片下载、大文件落盘）
`.catch(() => {})` 保证清理失败不会让 prompt 报错——**清理永远不该破坏主流程**。

## 4. 其他方法

```ts
supportsImages(): boolean {
  return this.runtime.session.model?.input?.includes("image") ?? false;
}

async abort(): Promise<void> {
  await this.runtime.session.abort();   // 中断当前生成
}

async dispose(): Promise<void> {
  await this.runtime.dispose();         // 释放 runtime 资源（空闲回收/删除会话时调用）
}
```

`supportsImages` 很关键：**模型不支持图片时，图片附件在处理器里会被降级**（见 05-9）。

## 5. RuntimeHost 与 SessionHost 的关系

```
SessionHost（会话单元）            RuntimeHost（runtime 管家）
├─ sessionKey                    ├─ sessionKey
├─ runtime  ────────────────► 持有 runtime 引用
├─ queue                        ├─ prompt(input)   ← 封装了全套执行上下文
├─ activeRun                    ├─ abort()
└─ lastUsedAt                   └─ dispose()
```

业务代码（message-handler）只碰 `host.runtimeHost.prompt(input)` 这一个方法，
**执行的全部魔法都封装在 RuntimeHost 里**。这是很好的「门面模式」应用。

## 6. 小结

| 职责 | 实现 | 教学点 |
|---|---|---|
| 创建 runtime | createRuntimeHost | 恢复/新建分支、工具注册时机、SDK 三部曲收敛 |
| 执行对话 | prompt | UI 上下文借用与归还、AsyncLocalStorage、双保险清理 |
| 中断 | abort | 一行转发给 SDK |
| 释放 | dispose | 生命周期终点 |
| 图片能力 | supportsImages | 能力探测驱动降级策略 |
