# 07 设计决策与权衡

> 本文汇总全项目最重要的设计决策，每个决策都回答「为什么这样做、替代方案是什么、代价是什么」。
> 适合面试讲项目、或者想理解作者思路的人。

## 决策 1：不改 Pi 核心，做成外部 transport 扩展包

**问题**：飞书集成可以直接改 Pi 源码，也可以做成扩展。
**选择**：扩展包。只通过 SDK 公开 API 接入。

**为什么**：
- Pi 是成熟产品，fork 维护成本高
- 扩展包可以独立版本化、独立发布（`package.json` 里 `pi.extensions` 字段）
- 用户不想要飞书时，不装即可

**代价**：受限于 SDK 公开 API，有些底层定制做不了（比如完全控制 session 恢复细节）。
**教学点**：优先做「顺 SDK 的集成」，而不是「改 SDK」。

## 决策 2：识别「单 active session」瓶颈，引入 SessionHostManager

**问题**：Pi 的 `AgentSessionRuntime` 是单 session 模型（终端场景合理）。
飞书是多用户、多群、多消息入口——**共用一个 runtime 必然串线**。

**选择**：`sessionKey → SessionHost` 的 Map。
每个 host 持有独立 runtime + queue + activeRun + context。

**不这么做会怎样**（设计文档列举的故障）：
- A 用户消息进 B 上下文
- A 生成时 B 的消息触发 session 切换
- B 点停止误中断 A
- 权限卡片串线
- 流式输出发错群

**教学点**：**识别底层模型的约束，再设计上层架构去满足真实场景**。
这是整个项目最重要的一步思考，比任何具体代码都值钱。

## 决策 3：每会话一个 PromptQueue，而不是全局锁

**问题**：同一会话的消息必须串行（避免上下文污染），但不同会话应并行。
**选择**：每个 SessionHost 一个 `PromptQueue`（Promise 链实现，26 行）。

**替代方案**：
- 全局锁 → 一个群生成时，所有私聊和其他群全被阻塞（差）
- 事件循环调度器 → 复杂度高，MVP 不需要

**代价**：每个会话多一个小对象，内存开销可忽略。
**教学点**：**锁的粒度 = 隔离的粒度**。按「业务隔离单元」加锁，不要全局加锁。

## 决策 4：用 AsyncLocalStorage 传递运行上下文

**问题**：`send_file_to_chat` 工具需要知道「当前在哪个 chat」，
但 Pi 的工具签名不允许带自定义参数。

**选择**：`runWithFeishuContext(ctx, run)` 包裹 prompt，
工具内部 `getFeishuContext()` 读取。

**替代方案**：
- 全局变量 → 并发时互相覆盖，完全错误
- 改工具签名 → 侵入 Pi SDK 的 ToolDefinition，违背决策 1
- 闭包注入 → 无法穿透 Pi 内部的工具调用链

**代价**：AsyncLocalStorage 有一定性能开销（可忽略）；上下文隐式传递，调试时可能不易察觉。
**教学点**：**隐式上下文（AsyncLocalStorage）适合「横切关注点」**——跨调用链传递而不污染签名。

## 决策 5：私聊按用户隔离，群聊默认共享

**问题**：会话粒度怎么定？
**选择**：

| 场景 | key | 理由 |
|---|---|---|
| 私聊 | `dm:{userOpenId}` | 一个用户一个上下文，连续 |
| 群聊默认 | `group:{chatId}` | 协作场景，大家接力讨论同一问题 |
| 群聊可选 | `group-user:{chatId}:{userOpenId}` | 需要个人上下文时开启 |

**替代方案**：全员 per-user → 群聊失去协作上下文。
**教学点**：**会话粒度是产品决策，不是技术决策**。
默认值选择「共享」（协作）而不是「隔离」（隐私），符合 MVP 场景。

## 决策 6：群聊必须 @ 机器人

**问题**：群聊里所有消息都处理？会刷屏、误触发。
**选择**：默认 `requireMention: true`，群消息必须 @ 机器人。
而且**未 @ 时静默拒绝**（不给群刷屏）。

**教学点**：**拒绝要分「静默」和「回应」**——策略违规的拒绝（未 @）静默，
配置问题的拒绝（私聊被禁用）回应，让用户能自查。

## 决策 7：任务状态用「一张卡的原地更新」

**问题**：生成中的状态怎么展示？每条消息都发新卡片会刷屏。
**选择**：开始发黄卡（停止按钮），结束 updateCard 变灰卡（完成/失败）。

**教学点**：**用消息的「状态机」替代「消息洪流」**。
飞书卡片支持原地更新，这是流式场景的最佳实践。

## 决策 8：权限确认桥接 ExtensionUIContext

**问题**：Pi 的扩展权限确认（confirm/select）是 TUI 交互，远程用户看不到。
**选择**：`createFeishuUIContext()` 把 select/confirm/notify 桥接成飞书卡片，
用 `pendingDialogs` 注册表挂起 Promise，按钮回调 resolve。

**价值**：**Pi 生态里已有的全部权限交互能力，飞书用户也能用**，
不用为飞书重新实现一套权限系统。

**教学点**：桥接的本质是「接口适配」——同一个 Promise 语义，换一个 IO 介质。

## 决策 9：模型输入按不可信数据对待（三层防线）

`send_file_to_chat` 的 filePath 是模型生成的，模型也可能被骗/出错：
1. 路径必须在 `allowedOutputDirs` 白名单内（防目录穿越）
2. 必须是文件
3. 大小不超过 `maxUploadBytes`

附件处理同样：文件名/sessionKey 消毒，防路径注入。

**教学点**：**即使调用方是「自己人」（模型），也要做输入校验**。
模型输出同样可能是恶意的或错误的。

## 决策 10：延迟多租户

**问题**：要不要做多企业支持？
**选择**：**不做**。只在数据结构里保留 `tenantKey` 字段。

**理由**：MVP 是一个飞书应用服务一个团队。多租户意味着
tenant router、tenant policy、tenant billing……复杂度成倍增长。

**教学点**：**为「未来可能的需求」只付「字段的代价」，不付「架构的代价」**。
这是最典型的工程取舍——YAGNI（You Aren't Gonna Need It）原则。

## 决策 11：宽容解析 + 严格补全的配置系统

**问题**：配置可能来自环境变量、用户手写文件、CLI，质量参差。
**选择**：
- `parsePartialConfig`：逐字段类型校验，坏字段忽略（宽容）
- `normalizeConfig`：必填缺失抛错，可选补默认值（严格）
- `mergeConfig`：env < 文件 < CLI，子对象逐层合并

**教学点**：**解析阶段宽容、使用阶段严格**。坏输入在边界被消化，
下游永远拿到完整、类型正确的配置。

## 决策 12：占位用语义化错误，不用空壳

webhook 和 SQLite 都是「接口已定义、实现未完成」。
占位方式是**抛带说明的错误**（`createWebhookNotImplementedError`），
而不是空函数或 TODO 注释。

**教学点**：**未实现的功能要「显式失败」**——调用方立刻知道
「为什么不能用、怎么绕过」，而不是在运行时才诡异报错。

## 决策 13：已知的待改进点（诚实清单）

| 项目 | 现状 | 风险 |
|---|---|---|
| `getHost` 首次并发 | 无锁，可能双创建 | 两条消息同时到新会话时可能建两个 host（WebSocket 事件基本有序，实际低概率） |
| `evictIdle` 无调度 | 没有定时器主动调用 | 空闲会话不回收，内存长期占用 |
| 卡片动作的耗时操作 | 同步 await | 会话切换/删除可能阻塞回调处理 |
| 多进程 | 无 | pendingDialogs、内存 host 都是进程内状态 |

**教学点**：**架构文档要包含「已知缺陷」**——面试被追问时，主动说比被戳穿强。

## 决策总结表

| # | 决策 | 一句话 |
|---|---|---|
| 1 | 扩展包不改核心 | 顺 SDK 集成 |
| 2 | SessionHostManager | 识别单 session 约束，按会话隔离 |
| 3 | 每会话队列 | 锁粒度 = 隔离粒度 |
| 4 | AsyncLocalStorage | 隐式上下文穿透调用链 |
| 5 | 私聊按人/群聊共享 | 会话粒度是产品决策 |
| 6 | 群聊必 @ | 静默拒绝策略违规 |
| 7 | 卡片状态机 | 原地更新替代消息洪流 |
| 8 | UI 桥接 | 复用 Pi 生态权限能力 |
| 9 | 三层文件防线 | 模型输入不可信 |
| 10 | 延迟多租户 | 只付字段的代价 |
| 11 | 宽容解析严格补全 | 边界消化坏输入 |
| 12 | 语义化占位 | 显式失败优于空壳 |
| 13 | 记录已知缺陷 | 诚实 > 完美 |
