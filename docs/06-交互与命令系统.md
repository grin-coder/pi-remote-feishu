# 06 交互与命令系统

> 对应源码：`src/bridge/message-handler.ts`（命令）、`src/bridge/card-actions.ts`（卡片动作）

## 1. 交互入口总览

用户有**两条**交互通道：

```
通道 A：发斜杠命令（文本）       通道 B：点卡片按钮
  /help  /sessions  /models     value: {cmd:"stop", sessionKey:...}
  /new  /stop  /reset  /status  value: {cmd:"model", ...}
        │                              │
        ▼                              ▼
  handleCommand（message-handler）  handleCardAction（card-actions）
        │                              │
        └──────────────┬───────────────┘
                       ▼
                SessionHostManager 操作
                （newSession / switchToMapping / abort / deleteMapping）
```

两条通道共享同一个 `SessionHostManager`——命令和按钮最终是同一套操作。

## 2. 命令系统（handleCommand）

### 2.1 分发结构

```ts
async function handleCommand(options): Promise<boolean> {
  const command = options.input.command;
  if (!command) return false;     // 不是命令 → 返回 false，走正常消息流程

  // 从 input 还原 FeishuIdentity（供 manager 使用）
  const routeIdentity = { appId, chatType, chatId, userOpenId, tenantKey?, senderName? };

  if (command.name === "help") { ... 发帮助卡片; return true; }
  if (command.name === "new" || command.name === "reset") { ... }
  if (command.name === "stop") { ... }
  // 需要 host 的命令：
  const host = await options.manager.getHost(options.input.sessionKey, routeIdentity);
  if (command.name === "sessions") { ... }
  if (command.name === "models") { ... }
  if (command.name === "status") { ... }
  return false;
}
```

**分层设计**：不需要 host 的命令（help/new/stop）先处理；
需要 host 的命令（sessions/models/status）统一 `getHost` 后再分发。

### 2.2 命令逐个分析

| 命令 | 行为 | 实现要点 |
|---|---|---|
| `/help` | 帮助卡片 | 直接 `sendCard`，不碰 host |
| `/new` | 新建会话 | `manager.newSession` + 文本提示 |
| `/reset` | 重置 | 先 `deleteMapping`（删旧映射），再 `newSession`（建新） |
| `/stop` | 中断生成 | `manager.abort`；无运行中任务时提示 |
| `/sessions` | 会话管理卡 | `store.listSessionMappings` → `buildSessionsCard` |
| `/models` | 模型选择卡 | `ModelRegistry` 列模型 → `buildModelsCard` |
| `/status` | 状态卡 | host.queue.depth、activeRun、channel.connected、当前模型 |

### 2.3 /reset 的语义（教学细节）

```ts
if (command.name === "new" || command.name === "reset") {
  if (command.name === "reset") {
    await options.manager.deleteMapping(options.input.sessionKey);  // 先删映射
  }
  await options.manager.newSession(options.input.sessionKey, routeIdentity);  // 再建新
  await options.channel.sendText(options.input.chatId, "已创建新的 Pi 会话。", { replyTo: options.input.messageId });
  return true;
}
```

- `/new`：在原 host 上新建 session（旧映射被覆盖）
- `/reset`：先删掉磁盘映射再新建——**彻底清空历史**，连「可恢复的旧会话」都不留

### 2.4 未知命令策略

`parseCommand` 只认集合里的 7 个命令，未知 `/xxx` 返回 `undefined`，
被当作普通消息**透传给模型**（不算命令）。
这是设计文档里的决策点：MVP 不拦截未知斜杠命令，避免误伤正常文本（比如用户讲「路径是 /tmp/xx」）。

## 3. 卡片动作系统（handleCardAction）

### 3.1 协议回顾

所有按钮 value：`{ cmd: string, ...附加字段 }`，四种 cmd：

```
stop       → 中止生成
session    → new / switch / delete（会话管理）
model      → 选择 provider/modelId/thinkingLevel
permission → 权限确认 resolve
```

### 3.2 两条处理路径

```ts
const value = options.event.actionValue;
const cmd = readString(value, "cmd");

if (cmd === "permission") {
  // 路径一：权限确认 → resolve 挂起的 Promise（05-7 详述）
  if (options.event.token) {
    await options.updateCardByToken(options.event.token, buildResolvedPermissionCard(value));
  } else {
    buildResolvedPermissionCard(value);
  }
  return;
}

const sessionKey = readString(value, "sessionKey");
if (!sessionKey) return;          // 没有 sessionKey 的卡片动作直接忽略

if (cmd === "stop") { await options.manager.abort(sessionKey); return; }
// 其他命令需要 host → 解析身份 → getHost → 操作
```

### 3.3 模型切换的完整闭环（示例）

```
用户发 /models
  └─► buildModelsCard：每个模型两个按钮
        value: {cmd:"model", sessionKey, provider, modelId, thinkingLevel:"off"|"high"}
  └─► 用户点「使用」
  └─► handleCardAction: cmd="model"
        ├─► identityFromStore 恢复身份
        ├─► manager.getHost(sessionKey, identity)
        ├─► ModelRegistry.find(provider, modelId) 校验存在
        ├─► session.setModel(model)
        ├─► session.setThinkingLevel("off")
        └─► updateCardByToken(token, 新模型卡)  ← 卡片原地更新，显示新选择
```

**卡片会原地刷新**：用户点完按钮，看到的模型卡片立刻变成新选择——交互闭环感很强。

## 4. 双通道的一致性

命令和卡片按钮在语义上**重叠**：

| 操作 | 命令通道 | 卡片通道 |
|---|---|---|
| 新建会话 | `/new` | 会话卡「新建会话」按钮 |
| 切换会话 | —（暂无命令） | 会话卡「切换」按钮 |
| 删除会话 | `/reset`（删当前） | 会话卡「删除」按钮 |
| 停止 | `/stop` | 停止卡「停止生成」按钮 |
| 选模型 | `/models`（打开卡片） | 模型卡「使用」按钮 |

卡片通道是命令通道的**图形化补充**——命令打开卡片，卡片按钮执行动作。
两者最终都调 `SessionHostManager` 的方法，行为完全一致。

## 5. 交互的并发安全回顾

1. **停止不串线**：`abort(sessionKey)` 只作用该会话的 activeRun
2. **模型切换不冲突**：`getHost(sessionKey)` 拿到的是该会话专属 runtime
3. **权限不串线**：dialogId 全局唯一，且 resolve 后立即删除
4. **队列状态可见**：`/status` 展示 `queue.depth` 和 `active`，用户能感知排队

## 6. 交互的扩展点

想加新命令/新卡片动作的步骤：

1. `types.ts` 的 `FeishuCommand` union 加名字
2. `message-normalizer.ts` 的 `COMMANDS` 集合加名字
3. `message-handler.ts` 的 `handleCommand` 加分支
4. `cards/` 建新卡片构建器
5. （可选）`card-actions.ts` 加 cmd 处理

## 7. 小结

| 通道 | 入口 | 分发器 | 操作对象 |
|---|---|---|---|
| 命令 | 文本 `/xxx` | handleCommand | SessionHostManager |
| 卡片 | 按钮 value | handleCardAction | SessionHostManager |

**教学要点**：
1. 命令与卡片是同一能力的两种前端。
2. 卡片按钮 value 是前后端协议，要小心设计。
3. 交互操作最终都收敛到 SessionHostManager，保持行为单一来源。
