# 03 核心概念

> 对应源码：`src/types.ts`
> 前置知识：已读完 `02-总体架构.md`

这一篇讲透四个核心概念，它们是理解整个项目的关键：

1. `sessionKey` —— 会话身份的字符串
2. `SessionHost` —— 会话隔离单元
3. `PromptQueue` —— 每会话串行队列
4. 上下文机制 —— `AsyncLocalStorage` 的魔法

## 1. sessionKey：飞书世界 → Pi 世界的映射钥匙

### 1.1 三种 key 格式

```ts
私聊:           dm:{userOpenId}              // 例如 dm:ou_abc123
群聊共享会话:     group:{chatId}              // 例如 group:oc_xxx
群聊按用户隔离:   group-user:{chatId}:{userOpenId}  // 可选模式
```

由 `src/bridge/conversation-router.ts` 的 `buildSessionKey` 生成：

```ts
export function buildSessionKey(config: FeishuConfig, identity: FeishuIdentity): string {
  if (identity.chatType === "private") {
    return `dm:${identity.userOpenId}`;          // 私聊：按用户
  }
  if (config.sessions.groupScope === "per-user") {
    return `group-user:${identity.chatId}:${identity.userOpenId}`;  // 群聊按用户
  }
  return `group:${identity.chatId}`;             // 默认：群共享
}
```

### 1.2 为什么私聊按「用户」而不是按「会话」

一个用户和一个机器人私聊，在飞书里通常只有一个会话。按 `userOpenId` 分，保证**同一个用户无论从哪个入口进来都是同一个 Pi session**，上下文连续。

### 1.3 为什么群聊默认「共享」

真实协作场景：一个群里大家 @ 机器人，共享同一个上下文，方便接力讨论。
群聊 prompt 里会带上「谁在说话」（见 `message-normalizer`），让模型知道当前对话人。

### 1.4 保留 `tenantKey` 的用意

数据结构里到处都有 `tenantKey?`，但 MVP 完全没用它做路由。
这是**为未来多租户预留的字段**——多个企业共用一套服务时，需要 `tenant:{tenantKey}:dm:{userId}` 这类 key。
现在不实现，只留字段，避免为不存在的需求付出复杂度（详见 07 的「延迟多租户」决策）。

## 2. SessionHost：隔离单元

### 2.1 结构

```ts
interface SessionHost {
  sessionKey: string;
  runtime: AgentSessionRuntime;  // 一个 Pi 运行时 = 独立的模型、上下文、session 文件
  queue: PromptQueueLike;        // 串行队列（防止同会话并发）
  activeRun?: ActiveRun;         // 正在跑的任务（可 abort、可查状态）
  lastUsedAt: Date;              // 空闲回收用
}
```

### 2.2 为什么是「host」而不是「session」

Pi 的 `AgentSessionRuntime` 本身就是 session 的概念。这里叫 **host（宿主）**，是因为它**寄宿**了一个 runtime：

- 一个 host 管理一个 runtime 的整个生命周期（创建 → 使用 → 空闲回收）
- host 额外持有队列、活跃任务、最后使用时间——这些都是 Pi runtime 没有的「飞书侧状态」

### 2.3 生命周期

```
首次消息到达 ──► getHost 发现没有 ──► 创建 runtime（打开/新建 session 文件）
                                     └─► 持久化映射（sessionKey → sessionFile）
活跃期间     ──► 每次消息更新 lastUsedAt
空闲超过 TTL ──► evictIdle 回收：dispose runtime、删内存 host
下一次消息   ──► 从 store 读回映射，重新打开 session 文件恢复
```

这个「内存缓存 + 磁盘持久化」的组合，是典型的热数据管理：
**运行中状态在内存，可恢复状态在磁盘**。重启进程后，用户之前的对话还在。

## 3. PromptQueue：每会话串行队列

### 3.1 为什么需要队列

Pi 的 `runtime.session.prompt()` 是异步的。如果同一会话里来了两条消息：

```
消息1：帮我写个程序（要生成 2 分钟）
消息2：不，先讲讲你的思路（1 秒后发来）
```

如果没有队列，两条 prompt 会**并发进入同一个 session**，上下文互相污染、输出交错。
所以要排队：消息2 必须等消息1 跑完。

### 3.2 实现（只有 26 行，全部核心）

```ts
export class PromptQueue {
  private tail: Promise<void> = Promise.resolve();
  private depthValue = 0;

  get depth(): number { return this.depthValue; }

  async enqueue<T>(run: () => Promise<T>): Promise<T> {
    this.depthValue += 1;
    const previous = this.tail;
    let release: () => void = () => {};
    this.tail = new Promise<void>((resolve) => { release = resolve; });

    await previous;          // 等上一个任务完成
    try {
      return await run();    // 执行当前任务
    } finally {
      this.depthValue -= 1;
      release();             // 释放，让下一个任务继续
    }
  }
}
```

### 3.3 链式 promise 的魔法（教学重点）

这个队列**没有数组、没有锁**，只用一个 `tail` 链：

```
初始:  tail = P0(已解决)

enqueue(A): previous=P0, tail=P1, await P0(立即过) → 执行 A
enqueue(B): previous=P1, tail=P2, await P1(等 A 释放) → 执行 B
enqueue(C): previous=P2, tail=P3, ...
```

每个新任务拿到「上一个任务的释放信号」作为自己的起点，同时把自己的释放信号交给下一个任务。
这就是**用 Promise 链实现串行化**的标准手法，值得背下来。

### 3.4 为什么不用全局锁

如果做一个全局锁：一个群生成很久时，**所有私聊和其他群都被阻塞**。
而本项目是**每个 SessionHost 一个 queue**：

```
queue(dm:alice)  ──► 串行
queue(dm:bob)    ──► 串行（与 alice 并行）
queue(group:c1)  ──► 串行（互不干扰）
```

测试文件 `test/prompt-queue.test.ts` 专门验证了这两点：
1. 同一队列串行（顺序严格）
2. 不同队列独立（b 可以在 a 结束前完成）

## 4. 上下文机制：AsyncLocalStorage

这是全项目**最魔法、也最重要**的一个设计。

### 4.1 问题

`send_file_to_chat` 工具执行时，需要知道「当前这条请求属于哪个 chat」。
但工具函数是 Pi 内部调用的，**没法通过参数把 chatId 传进去**。

### 4.2 方案：`src/feishu/context.ts`

```ts
import { AsyncLocalStorage } from "node:async_hooks";

const storage = new AsyncLocalStorage<FeishuRunContext>();

export function getFeishuContext(): FeishuRunContext | undefined {
  return storage.getStore();
}

export async function runWithFeishuContext<T>(context, run) {
  return await storage.run(context, run);
}
```

### 4.3 工作方式

```
runWithFeishuContext({chatId, sessionKey, channel, uiContext, config}, async () => {
  await runtime.session.prompt(text);   // ← 这棵异步树的任意深处
});
```

在 `run` 期间**创建的所有异步回调**（包括模型调工具、工具内部 await），
都能通过 `getFeishuContext()` 拿到同一份 context。Promise 执行结束就自动清空。

这解决了工具、权限卡片回调「从哪里来」的问题，且**没有把上下文塞进参数列表**——
Pi 的 `ToolDefinition` 签名完全不用改。

### 4.4 为什么安全

- `AsyncLocalStorage` 是 Node 官方 API，按异步执行上下文隔离
- 不同 SessionHost 的 prompt 在不同上下文里跑，互不污染
- 用完后 `storage.run` 自动清理，无需手动删除

### 4.5 使用方（两个）

| 使用方 | 位置 | 用途 |
|---|---|---|
| `send_file_to_chat` 工具 | `src/tools/send-file-to-chat.ts` | 拿到 `channel` + `chatId` 发文件 |
| `createFeishuUIContext` | `src/bridge/ui-context.ts` | 权限确认卡片发到正确的 chat |

## 5. 核心概念小结

| 概念 | 一句话 | 位置 |
|---|---|---|
| sessionKey | 飞书会话的唯一身份字符串 | `conversation-router.ts` |
| SessionHost | 一个 Pi runtime + 队列 + 活跃任务的隔离单元 | `session-host-manager.ts` |
| PromptQueue | Promise 链实现同会话串行、跨会话并行 | `prompt-queue.ts` |
| AsyncLocalStorage | 让任意深度的异步代码拿到「当前飞书请求上下文」 | `feishu/context.ts` |
