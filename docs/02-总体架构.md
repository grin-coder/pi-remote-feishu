## 2. 分层思想

整个系统可以按「谁依赖谁」分成四层：

```
┌─ Layer 4: 应用层（组合一切）
│    bin/pi-remote-feishu.ts          把 config/channel/store/manager 组装起来
│    extensions/index.ts       把工具注册给 Pi
├─ Layer 3: 桥接层 bridge/ ★ 核心
│    message-handler  orchestration（编排）
│    conversation-router / message-normalizer / session-host-manager
│    runtime-host / prompt-queue / stream-renderer / ui-context / card-actions
├─ Layer 2: 基础设施
│    feishu/channel.ts（外部通信）
│    cards/（展示）
│    attachments/（输入预处理）
│    store/（持久化）
│    tools/（Pi 工具）
├─ Layer 1: 类型契约
│    types.ts（所有共享类型，全项目的地基）
└─ 外部依赖：Pi SDK / 飞书 SDK / TypeBox
```

**依赖规则**：上层依赖下层，下层绝不反向依赖上层。
比如 `cards/` 只依赖 `types.ts`，不知道 `bridge/` 的存在；
`feishu/channel.ts` 只暴露 `FeishuChannel` 接口，调用方拿到的是接口而不是具体类。

## 3. 两个进程的启动路径

### 3.1 Transport Host 启动（`src/bin/pi-remote-feishu.ts`）

```ts
async function main() {
  const cli = parseArgs(process.argv.slice(2));        // ① 解析 CLI 参数
  const config = loadConfig(cli.config);               // ② 合并配置（env < 文件 < CLI）
  const channel = createFeishuChannel({...});          // ③ 创建飞书通道（包 SDK）
  const store = createStore(config);                   // ④ 创建存储
  const manager = new SessionHostManager({...});       // ⑤ 创建会话管理器

  channel.onMessage((message) => {                     // ⑥ 注册消息回调
    handleFeishuMessage({ config, channel, store, manager, message });
  });
  channel.onCardAction((event) => {                    // ⑦ 注册卡片按钮回调
    handleCardAction({...});
  });
  channel.onError((error) => console.error(error.message));

  await channel.connect();                             // ⑧ 连接飞书 WebSocket
  await new Promise<void>((resolve) => {               // ⑨ 挂起等待 SIGINT/SIGTERM
    process.once("SIGINT", shutdown);
    process.once("SIGTERM", shutdown);
  });
}
```

这段代码本身就是「组合根」（Composition Root）：
**config / channel / store / manager 都是在这里创建、在这里注入**，模块之间不互相 new。

注意两个细节：

1. `channel.connect()` 前的所有回调都已注册——因为 WebSocket 一旦连上，消息可能立刻涌来，回调必须先就位。
2. 进程最后挂在一个 `Promise` 上，只有收到退出信号才会 `disconnect` 并退出。这就是「长连接进程」的典型写法。

### 3.2 Pi Extension 加载（`src/extensions/index.ts`）

```ts
export default function feishuExtension(pi: ExtensionAPI): void {
  pi.registerCommand("feishu", {...});                // TUI 内 /feishu 命令
  try {
    const config = loadConfig();                       // 尝试读配置
    pi.registerTool(createSendFileToChatTool(config)); // 注册发文件工具
  } catch {
    // 配置缺失时优雅降级：等 agent 启动后提示一次
    pi.on("agent_start", (_event, ctx) => {
      ctx.ui.notify("Feishu config not found; send_file_to_chat is not registered.", "warning");
    });
  }
}
```

要点：

- **这个文件不碰飞书连接**。它只是「如果配置存在，就把工具注册给 Pi」。
- 配置缺失不崩溃，而是注册一个 `agent_start` 事件，提醒用户。
- `package.json` 中的 `"pi": { "extensions": [...] }` 告诉 Pi 包管理器加载它。

## 4. 核心数据结构（地基）

所有类型定义在 `src/types.ts`，它是整个项目的地基。理解架构前，先认识这几个：

### 4.1 `FeishuChannel` —— 通道抽象

```ts
interface FeishuChannel {
  connect(): Promise<void>;
  onMessage(handler: (message: FeishuMessage) => void): void;
  onCardAction(handler: (event: FeishuCardAction) => void): void;
  sendText / sendMarkdown / sendCard(chatId, content): Promise<SendResult>;
  streamMarkdown(chatId, producer): Promise<void>;   // 流式
  updateCard / updateCardByToken(messageId|token, card): Promise<void>;
  sendFile / sendImage(chatId, filePath): Promise<void>;
  downloadResource(messageId, fileKey, type): Promise<Buffer>;
}
```

为什么定义成接口而不是类？——**上层只依赖接口**，测试时可以轻松 mock 通道（见测试目录里 `send-file-to-chat.test.ts` 的用法）。

### 4.2 `FeishuMessage` —— 归一化后的消息

```ts
interface FeishuMessage {
  messageId: string;
  chatId: string;
  chatType: "private" | "group";
  userOpenId: string;
  senderName?: string;
  tenantKey?: string;
  text: string;
  mentionedBot: boolean;      // 是否 @ 了机器人（群聊策略要用）
  resources: FeishuResource[];// 附件（图片/文件等）
  raw: unknown;               // 保留原始数据，方便排查
}
```

### 4.3 `NormalizedPiInput` —— 给 Pi 的输入

```ts
interface NormalizedPiInput {
  sessionKey: string;
  chatId: string;
  messageId: string;
  userId: string;
  chatType: ChatType;
  text: string;               // 拼好上下文的 prompt 文本
  images: ImageInput[];       // base64 图片
  attachmentNotes: string[];  // 附件说明
  command?: FeishuCommand;    // /help /stop 等
}
```

### 4.4 `SessionHost` —— 每会话隔离单元

```ts
interface SessionHost {
  sessionKey: string;
  runtime: AgentSessionRuntime;  // Pi 运行时
  queue: PromptQueueLike;        // 串行队列
  activeRun?: ActiveRun;         // 当前正在跑的任务（可 abort）
  lastUsedAt: Date;              // 用于空闲回收
}
```

## 5. 消息流全景（一分钟版）

```
飞书用户
  └─► channel.onMessage
       └─► handleFeishuMessage
            ├─► routeConversation       判定策略 → sessionKey
            ├─► manager.getHost         拿/建 SessionHost（含 runtime）
            ├─► processAttachments      附件 → 图片/文本/临时文件
            ├─► normalizeMessage        拼成 Pi 输入
            ├─► handleCommand?          是命令 → 卡片回复，结束
            └─► host.queue.enqueue
                 ├─► 发「Pi 正在处理」停止卡
                 ├─► runtimeHost.prompt → session.prompt(text)
                 │    ├─► stream-renderer  事件 → 流式文本
                 │    └─► ui-context       权限确认 → 卡片 → 等按钮
                 ├─► 更新停止卡为完成/失败
                 └─► 清理临时文件、释放 activeRun
```

## 6. 架构小结

| 设计 | 目的 |
|---|---|
| 接口化 `FeishuChannel` | 屏蔽 SDK，可测试，可替换 |
| bridge 层独立 | 飞书世界和 Pi 世界的翻译官，全部编排逻辑集中在这 |
| 组合根在 bin | 模块全部依赖注入，无全局可变状态（除了 AsyncLocalStorage） |
| 双进程 | transport 长连接与 Pi 扩展能力解耦 |
| types.ts 统一契约 | 所有模块共享一套类型，避免「各写各的」 |
