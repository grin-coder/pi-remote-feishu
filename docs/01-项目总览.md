# 01 项目总览

> 对应源码：整个 `src/` 目录
> 前置知识：Node.js + TypeScript 基础

## 1. 这个项目是什么

`pi-remote-feishu` 是一个让 **AI 编码代理 Pi Agent** 通过 **飞书（Feishu/Lark）** 与用户对话的扩展包。

一句话概括：

> 把飞书变成 Pi Agent 的「远程终端」——用户在飞书私聊/群聊里发消息，Pi 在服务器上干活，
> 把思考过程、工具调用、生成的文件全部投射回飞书。

它不是一个独立聊天机器人，而是 **Pi 的一个 transport（传输通道）扩展**。

```
┌─────────────────┐        ┌───────────────────────┐        ┌──────────────┐
│  飞书 App       │  ◄────► │  pi-remote-feishu 服务进程    │  ◄────► │  Pi Agent    │
│  (私聊/群聊)     │  WebSocket│ (transport host)      │   SDK   │  (runtime)   │
└─────────────────┘        └───────────────────────┘        └──────────────┘
```

## 2. 它解决的核心问题

Pi Agent 的设计目标是终端使用场景，它的核心运行时 `AgentSessionRuntime` 是**单 active session 模型**：

```text
AgentSessionRuntime
  -> runtime.session        // 当前只有一个活动 session
  -> runtime.switchSession()
  -> runtime.newSession()
```

终端里天然只有一个「当前对话」，所以这个模型没问题。
但飞书是**多用户、多群、多消息入口**。如果所有飞书消息共用一个 runtime.session，会出大乱子：

| 场景 | 出问题 |
|---|---|
| A 用户发消息 | 消息进入 B 用户的上下文，串线 |
| A 生成时 B 发消息 | 触发 session 切换，A 的任务被打断 |
| B 点「停止生成」 | 误中断 A 的任务 |
| 权限确认卡片 | 两个用户同时等待确认，resolve 串线 |
| 流式输出 | 发错群、发错私聊 |

因此本项目引入了**会话隔离架构**（详见 `03-核心概念.md`）：

```text
ConversationRouter
  -> SessionHostManager
       -> dm:alice        -> SessionHost A -> Runtime A + Queue A
       -> dm:bob          -> SessionHost B -> Runtime B + Queue B
       -> group:chat-123  -> SessionHost C -> Runtime C + Queue C
```

每个会话（用户私聊/每个群）拥有**独立的** Pi runtime、串行队列、活跃任务标记和飞书上下文，
互不干扰，还能并发运行。

## 3. 两个进程的边界（最重要的架构认知）

项目把系统拆成**两个独立的部分**，这是整份代码的骨架：

### 3.1 Transport Host（传输服务进程）

- 入口：`src/bin/pi-remote-feishu.ts`，命令 `pi-remote-feishu serve`
- 是一个**长期运行的进程**
- 负责：连接飞书 WebSocket、接收消息、处理卡片按钮、维护会话、调用 Pi runtime
- 它「使用」Pi 的 SDK，但不修改 Pi 核心

### 3.2 Pi Extension（Pi 扩展）

- 入口：`src/extensions/index.ts`
- 由 **Pi 自己加载**（通过 `package.json` 里的 `pi.extensions` 字段）
- 负责：给 Pi 注册工具（`send_file_to_chat`）、注册 `/feishu` 命令、注入 prompt 指引
- 它**不打开飞书连接**——飞书连接只属于 transport host

为什么拆开？

- transport host 是「嘴和耳朵」（长连接、收发消息）
- extension 是「手」（模型运行时能调用的能力）
- 两者解耦后：不启动 transport 时，Pi 依然正常使用；extension 不需要关心飞书 SDK 细节

## 4. 源码目录结构

```
src/
├── bin/
│   └── pi-remote-feishu.ts          # CLI 入口：解析参数、组装各组件、启动服务
├── config/
│   ├── schema.ts             # 配置的类型解析/合并/默认值（配置系统核心）
│   └── load-config.ts        # 配置加载：env > 文件 > CLI 优先级
├── feishu/
│   ├── channel.ts            # 飞书通道封装（SDK 的皮，屏蔽原始类型）
│   ├── context.ts            # 飞书运行上下文（AsyncLocalStorage 魔法）
│   └── webhook.ts            # Webhook transport（占位，未实现）
├── bridge/                   # ★ 核心业务层：把飞书世界和 Pi 世界桥接起来
│   ├── conversation-router.ts    # 消息 → sessionKey 的映射规则
│   ├── message-normalizer.ts     # 飞书消息 → Pi 输入（去@、识别命令、拼 prompt）
│   ├── session-host-manager.ts   # 会话宿主管理（查找/创建/回收）
│   ├── runtime-host.ts           # 单个 Pi runtime 的封装
│   ├── prompt-queue.ts           # 每会话串行队列
│   ├── message-handler.ts        # 消息处理主流程（命令分发 + 入队执行）
│   ├── stream-renderer.ts        # Pi 事件流 → 飞书流式输出
│   ├── ui-context.ts             # Pi 的 ExtensionUIContext → 飞书卡片
│   └── card-actions.ts           # 飞书卡片按钮 → 对应的管理操作
├── cards/                    # 飞书卡片 JSON 构建器
│   ├── common.ts             # 卡片基础组件（文本、按钮、下拉、header）
│   ├── help.ts / models.ts / sessions.ts / status.ts / stop.ts / permission.ts
├── attachments/
│   ├── processor.ts          # 附件下载与分类（图片/文本/大文件）
│   ├── mime.ts               # MIME 推断、是否文本判断
│   └── temp-files.ts         # 临时文件写入与清理
├── store/
│   ├── store.ts              # 存储工厂（json / sqlite 占位）
│   └── json-store.ts         # JSON 文件存储（会话映射持久化）
├── tools/
│   └── send-file-to-chat.ts  # Pi 工具：模型生成文件后发回飞书
├── extensions/
│   └── index.ts              # Pi 扩展入口
├── index.ts                  # 包对外导出
└── types.ts                  # ★ 全部类型定义（建议第一个读的文件）
```

## 7. 小结

读到这里你应该记住三件事：

1. **这是一个 transport 扩展包**，不改 Pi 核心，只是把飞书接进来。
2. **核心难点是并发会话隔离**：飞书多用户 vs Pi 单 session，用 `SessionHostManager` 解决。
3. **两个进程边界**：`pi-remote-feishu serve`（传输）+ Pi extension（能力注册），各自独立。
